## Savings assessment (estimate withdrawn)

As of this capture, verified resident-RAM savings from the optimization work
are **zero**. The previously proposed **100–300 MiB** target is withdrawn:
the captures do not establish a defensible total savings estimate.

Evidence for possible experiments, without a predicted savings total:

- GUI texture staging creation paths account for 175.965 MiB resident backing,
  and a separate capture shows retained staging resources used for one upload.
  This is the first bounded release/recreate experiment to investigate. The
  backing-path total is not a guaranteed reclaimable resource footprint;
  resource lifetimes and driver retention can reduce actual savings to zero.
- GameData child chunks contain 119.212–147.216 MiB in allocation headers,
  rounding and alignment, using verified pool request-size bounds and exact
  bucket/vector/map allocation sizes. This excludes record-body overhead and
  NT heap overhead. Some headers/alignment remain necessary, so recovering
  all of this is not realistic. It is a subset of the broader allocator
  overhead already reported, not another amount to add.
- Bone-assignment trees use 110.105 MiB of chunks. The native node request is
  56 bytes, with 24 additional bytes per 80-byte allocator chunk (33.032 MiB
  total). Packing only the 12-byte assignment fields would use 16.516 MiB,
  giving approximately 93.589 MiB theoretical representation headroom before
  indexes or equivalent functionality. This is a substantial native container
  redesign, not a safe drop-in saving or permission to discard skinning data.
- Only 15.569 MiB of the inspected Ned allocator was resident free/cache
  chunks. The evidence does not support a large blanket cache-flush saving.

Neither a 400 MiB nor an 800 MiB–1 GiB resident saving is demonstrated.
Compiled native container layouts, mutation paths, ownership,
save/load behavior and driver retention limit what a runtime plugin can safely
change. No saving is credited until a controlled same-save resident-RAM A/B
measurement demonstrates it; logical payload reductions do not qualify.

## Change in diagnostic approach

Further allocator/container reverse engineering is deferred until controlled
whole-game comparisons establish which change actually affects memory use.
The existing same-process observations show private resident RAM falling from
2426.742188 MiB during loading (00:28:06 UTC), to 2310.281250 MiB near the Hub
(00:28:24), to 2267.882812 MiB at 00:42:51. These sparse samples do not establish
a continuing resident-memory leak, and the loading sample is not a main-menu
baseline. Committed memory increased over these observations; it is a separate
metric and does not reverse the resident-memory result.

The first useful controlled comparison is the same save/settings with the
base game versus the current plugin configuration, starting a fresh process
for each and allowing loading to settle. This isolates the total effect of
our changes and enabled diagnostics before another native optimization.
Subsequent comparisons should change one verified game setting or loading
condition at a time and record private resident RAM, commit and graphics
memory separately. A practical effect must repeat in matched runs before it
is used to prioritize implementation. No game files or settings were changed
while reassessing these saved captures.

### Actual loading behavior

- GameData file loader `0x6c0b50` reads a file's record count and constructs and
  fills each record/property map before returning. Records within a selected
  file are eagerly expanded. Reference resolution can separately be lazy:
  `GameDataReference::getPtr` at `0x6bee10` resolves and caches its pointer on
  first access. Lazy reference linking does not mean lazy record allocation.
- Interior manager method `0x54c330` checks loaded flag `+0x180`. On first use,
  it loops the configured mod list, appends `interiors.level` to each source
  folder, loads those files, and marks the manager loaded. It retains the
  shared library for subsequent interior lookups. The live list contains the
  root, Newwworld, Dialogue and rebirth folders; the loaded flag was 1.
  Those four authored files total 25,127,471 bytes (23.963 MiB) on disk and
  contain 44,012 serialized records before loading and merge/deletion handling.
  Their disk size is not a resident-memory measurement. The exact reason for the difference from the
  live 43,018 interior records was not determined.
- Manager reload `0x6c3d20` loads into a temporary container, merges records into
  the destination, and destroys the temporary. This path does not establish
  retention of a complete duplicate source container after loading.
- SaveManager load `0x373f00` loads `quick.save` into the global save manager.
  SaveFileSystem load `0x4746e0` sets the current save location and builds a
  file index. An index of saved filenames is not expanded record payload.
- Zone activation `0x9ffad0` loads its authored `zone.x.y.zone` and then its
  saved `zone/` overlay into the zone's container. The inspected path supports
  zone payload loading on activation, not eager parsing of every world-zone
  save file when the save is selected.
- Zone deactivation `0x9fe980` handles saving and destroys live zone objects;
  ZoneMap deactivation `0xa0a4f0` destroys map content and terrain collision.
  Map-content destructor `0xa00980` destroys its record container. Container
  clear `0x6bf510` queues mutable records for deferred destruction and clears
  its indices; shared read-only records are deliberately preserved. Queue
  flush `0x6bc390` invokes record deleting destructors. The destruction-phase
  caller `0x79d8a0` invokes that flush; its runtime cadence was not measured.

Consequently, the evidence does not support replacing a supposed
whole-world-save load with zone streaming: zone streaming already exists.
The large retained shared definition/interior representation is the more
specific subject for further investigation. Loading interior libraries by
individual layout, or compiling more compact runtime definitions, would
require proving lookup, shared-reference, mutation and save behavior first.
No RAM saving from either approach is demonstrated here.
