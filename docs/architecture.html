01 / System map

A small core.
Explicit boundaries.

This is an in-process native modding platform. The host loads into Kenshi, bundles core features, and lets separately compiled DLLs contribute behavior without rebuilding the host.

Kenshi loads the host as an Ogre plugin. The host establishes known native entry points, provides settings and diagnostics, and coordinates two kinds of participants: built-ins linked into the host and optional DLLs in RE_Kenshi_Rust/plugins/. Both can use the public operation broker. The safe SDK makes independent plugins look like ordinary Rust Plugin implementations inside their own module.

INTERACTIVE / Select a layerCompile-time libraries + runtime services

The host turns capabilities into services

The root crate builds RE_Kenshi_Rust.dll. It coordinates startup, external DLL discovery, hook reservations, the native Options tab and the generic operation registry. Feature crates implement the specialized native providers. This map shows responsibilities, not separate processes or a strict one-way dependency graph.

src/plugin.rs · src/extensions.rs · src/platform.rs · plugins/*

Policy chooses behavior

Examples include a desired rain style, a shader-source transform or an effect’s sixteen parameters. Policies can register before the renderer or other native resource exists.

A provider owns execution

A verified adapter advertises a contract, intercepts a particular native operation, copies the necessary data, applies composed rules and validates the result before native use.

Where content tools fit. FCS and asset tools still author definitions, templates and content. Runtime plugins operate during play. A combined mod can use both; this architecture does not replace Kenshi’s content pipeline.

02 / Bootstrap & lifecycle

Register first.
Activate second.

Startup has a preparation barrier: participating built-ins and discovered DLLs register their desired behavior before providers are installed.

The installer places RE_Kenshi_Rust in Plugins_x64.cfg before renderer plugins, replacing the active original RE_Kenshi entry while preserving backups. Ogre calls the exported dllStartPlugin() outside Windows’ DllMain. The host resolves the inspected Ogre root getter and pins the relevant modules so stored function addresses and trampolines remain valid.

STARTUP / Step through the sequence01 / 06

Ogre enters the host

dllStartPlugin crosses a panic-containing C entry point into plugin::start. The lifecycle mutex serializes startup and shutdown; an already-active host returns without installing duplicate hooks.

Preparation is a lifecycle phase.
  1. Resolve and reserve native targets.The Ogre getter’s signature is inspected; UI and gameplay adapters perform their own checks. Module pinning precedes retaining executable pointers. Cooperative reservations prevent participating plugins from claiming the same address.
  2. Prepare every participating composition.Built-ins load validated settings and run register. Discovered DLLs negotiate their descriptor and run the mandatory rekenshi_plugin_prepare export. Preparation failures clean up pending ownership.
  3. Commit the host hooks and prove forwarding.A detour transaction coordinates patching with existing threads suspended. The host compares the getter’s original result with the patched entrance and checks the call counter. Failure triggers rollback.
  4. Install providers, then start external plugins.Gameplay and managed callbacks become ready; built-ins install in registry order, followed by DLLs in configured order. Resource-dependent work can remain pending until a valid native use occurs.

Explicit enabled entries in plugins.toml load first, in listed order; discovered unlisted DLLs follow in filename order. A disabled explicit entry wins over discovery. Dependencies must already be available when a plugin installs: the loader does not topologically sort DLLs for you. The normal bundled registry is mounted when modpack.toml exists.

The barrier has a defined reach. It covers participating plugins discovered for this startup. It cannot rewind native work that happened before the host, nor coordinate an unrelated framework’s private detours. late() sees earlier broker-observed uses only.

03 / The DLL boundary

Rust on both sides.
C in between.

Independent Rust DLLs are separate compilation units. The platform avoids relying on a shared Rust object layout or allocator across them.

export_plugin! generates a DLL entry descriptor, preparation, settings and dispatch exports. The host and SDK negotiate versioned, size-checked C tables. The frozen HostV1 and PluginV1 layouts remain intact while optional services add new capabilities, including the independently negotiated rekenshi_platform_api.

Plugin DLL

Local Rust ownership

  • Plugin trait implementation and mutable state
  • Closures, captured values and allocations
  • SDK handles that unregister on removal or drop
  • Panic containment at its own callback boundary

Host / provider DLL

Local native ownership

  • Native bindings and detour trampolines
  • Engine objects and allocator-specific releases
  • COM references, shaders and GPU buffers
  • Registries that authorize owner tokens
C ABI: version + size + portable fields + bounded buffers + function pointers

Opaque means opaque. A handle or callback context does not grant the receiving DLL permission to inspect another DLL’s Rust object. Function pointers return execution to the owning implementation. Safe clients copy results into their own Rust values.

Compatibility is explicit

Wrong versions, sizes or invalid descriptors are rejected. An absent optional service is a capability failure. Keeping the original V1 table shape does not guarantee an old DLL will load: the current loader also requires the preparation export.

Native code remains trusted

Owner tokens and hook reservations coordinate modules. They do not sandbox them. A native access violation or incorrect C++ binding can still crash Kenshi, even when ordinary SDK callbacks are panic-contained.

04 / Public operation broker

One operation.
Many contributors.

Named contracts let providers and policies discover each other without adding a host enum for every new feature.

A provider publishes a namespaced protocol with a schema, composition mode, payload bounds, native execution lane and evidence description. Consumers register desired rules against that name. A rule can stay pending while its provider is absent, and survive compatible provider recreation. Publishing a descriptor records the provider’s claim; it does not independently verify the native evidence.

Both rules contribute; the lowest requested visibility wins.

  1. Copy the operation’s input.The provider keeps engine objects and native streams private. Opt-in policies receive bounded portable metadata and payload bytes, with captures serialized separately from ordinary plugin state.
  2. Resolve deterministic order.Priority, identity and owner break ties. Optional before/after identities add ordering edges. Cycles, duplicate identities, incompatible modes and conflicting exclusive policies are rejected. Changing ordering after first use requires restart.
  3. Compose, then validate.Synchronous transforms produce a candidate result. A failed composition discards partial output. The native provider checks replacements before committing and preserves the original operation on validation failure. This is not general rollback for irreversible side effects.
  4. Track revision and generation.A policy revision says desired behavior changed. A provider generation says the native provider was recreated. A stable SHA-256 policy manifest represents identities, versions and ordering constraints without process-local tokens or generations.
  5. Revoke before retiring resources.Owner-checked removal waits for admitted callbacks; provider revocation quiesces callbacks before native resource retirement. Compatible desired registrations remain pending until a provider returns.

Example: shader compilation

The source transform runs before cache lookup. The cache hashes transformed source, compiler inputs and the policy manifest. On a valid hit, native compiler-owned blobs are reconstructed. On a miss, the original compiler runs; failed compilations are not cached.

Example: declarative effects

PostProcess owns a desired HLSL-and-constants registration. The graphics provider later realizes it as shaders and buffers. Removing the rule retires its GPU copies on a subsequent eligible draw or shutdown.

Bounded by design. The broker retains at most 1,024 contract names and 8,192 registration handles, including cleanup tombstones over process life. Operation payloads are capped at 16 MiB. Registration churn can exhaust this budget; handles are not an unlimited per-frame scratch space.

05 / Threads, events & callbacks

Execution belongs
to a specific lane.

There is no universal plugin tick. Each interface defines when it runs and what state it can touch.

InterfaceExecution pointContract
Ogre observerAfter the original root getter returns; possibly concurrent.Observation only; no native pointer enters the closure.
UI observerAfter MyGUI’s frame event, on the UI thread.Receives elapsed seconds; this is not a draw callback.
Operation transformSynchronously on the provider’s advertised native lane.Copied input/output, independently serialized captures.
Lifecycle / domain eventDeferred serial delivery after the verified game update and command dispatch.Ordinary plugin state serialized with settings and stop.
Worker threadPlugin-owned execution.Read copied snapshots, queue commands, do owned I/O; join on stop.

Observers preserve native execution

The original function forwards through the hook’s trampoline first. Observers run in registration order. Reentering the same hook still forwards native work, but suppresses nested observers. Calling the catalog’s patched entry from its detour would recurse; forwarding uses the detour’s own trampoline.

Events are copied occurrences

Readiness watches replay current status; domain events represent future occurrences. A queued historical event does not make a revoked object usable. Overflow disables the observer with an error rather than silently dropping data. Each serial dispatch delivers at most 64 deferred records per plugin.

Failure has ownership. A callback panic quarantines its owner and requests a Kenshi restart. New registrations and settings changes for that faulted owner are rejected while independent work can finish. Synchronous lifecycle/settings changes from callbacks are rejected to avoid waiting on the current stack. Shutdown removes managed callbacks and waits for admitted calls before cleanup.

Ogre getter counts are not simulation time. UI frames do not establish world readiness. On an unsupported executable, automatic game-lane delivery is unavailable even if a DLL loaded successfully. Headless fixtures use an explicit copied-data dispatch export.

06 / Gameplay service

A copied world.
A queued intent.

A plugin can inspect player characters or request supported commands without borrowing the game’s live C++ objects.

The native adapter hooks the inspected PlayerInterface::update point for the supported Kenshi 1.0.68 fingerprint. The host captures owned roster data and dispatches queued commands on the game lane after that update. World reset, clear and destruction invalidate the current world IDs before their native state becomes stale.

01 / CAPTURE

Native state

The host reads player characters on the verified game thread.

02 / COPY

Owned snapshot

World generation, opaque IDs, optional stats and health.

03 / REQUEST

Command ticket

A plugin submits a bounded, capability-checked intent.

04 / DISPATCH

Result or rejection

The game lane validates IDs and performs the native call.

Availability and capability are separate
NoWorld means nothing has been captured. AdapterUnavailable means the native binding cannot supply it. An available service still exposes per-command capability bits.
IDs belong to a world generation
Discard character and squad IDs when snapshot.world changes. They are neither native addresses nor persistent save-game identities. A copied snapshot remains readable after the live world changes.
Applied means dispatched
MoveTo, Stop, roster-teammate Follow and standing orders have initial adapter support. Attack exists in the SDK but is unsupported by that adapter. Applied does not mean arrival or AI completion.
Queues have a lifecycle
Each plugin may retain 128 queued commands plus uncollected results. Taking a terminal result frees its slot. Requests over five seconds old expire when the game next processes the queue; a stalled game can leave them pending meanwhile.

Concrete example: the squad inspector. The current implementation subscribes to roster-change events, copies a snapshot into owned JSON, and signals a bounded, coalescing file worker. The worker writes only changed data and joins during stop. This replaces the polling description still present in older gameplay documentation.

Fields such as position, selection and individual health values are optional. Missing anatomy is not zero health, and unknown selection is not false. Stats are base/raw values; health uses native units. World/save/import phases and arbitrary NPC spawning are not implied by this roster service.

07 / Shared graphics backend

Follow a frame
through the renderer.

Effects share one backend. The provider owns D3D11 state and native resources; effect DLLs contribute copied HLSL, priority and sixteen finite parameters.

Conceptual render sequence / not a timing trace

Recognized target + depth binding.

Tonemap resolve

HDR becomes LDR scene color.

Ordered effects

Copied scene → pass A → pass B.

Restore & continue

Restore modified state; native rendering proceeds.

The public effect stage is post-tonemap. In the documented live capture, the GUI renders downstream.

Recognize a supported scene pass

The backend observes fullscreen Draw(3/4). It recognizes HDR lighting using an R11G11B10_FLOAT target with R32_FLOAT depth at PS t2, then an HDR-to-BGRA8/RGBA8 resolve on that immediate context. Eligible targets are single-mip, single-slice, single-sample and at least 640 × 360.

Copy, compose, restore

Each effect receives current LDR scene color at PS t0, a linear-clamp sampler at s0, and four float4 constants at b0. Passes run in ascending priority with public identities resolving ties. Device, size or format changes rebuild provider-owned resources lazily.

State restoration is part of correctness. The provider preserves the shader stages and class instances it modifies, render/depth targets, blend and depth-stencil settings, rasterizer and viewports, input layout/topology, and PS t0/s0/b0. It skips injection around stream output, output-merger UAVs or predication whose hidden state it cannot safely preserve.

A runtime GPU error disables the current rendering resources; a changed desired rule can rebuild them. This SDK does not expose depth, temporal history, motion vectors, arbitrary pre-fog stages or hot reload. Experimental built-in ambient occlusion uses separate deferred-lighting contracts and scoped constants; its depth use is not a depth API for postprocess DLLs.

Weather changes appearance

The weather provider intercepts verified particle-render paths. Built-in tone-down scales supported weather visibility to 35%; a rain-refinement DLL can separately request thinner streaks and camera fade. Scoped state restores native dimensions; emitter creation and simulation remain native.

Dark UI preserves assets

The UI adapter classifies native skins and changes colors on the UI thread, retaining original colors for reversal. It preserves artwork, layout and meaningful status colors, removes lifetime records before reuse, and exposes copied skin observations rather than live widget pointers.

Reuse work.
Respect the original owner.

Availability is a runtime result. Named hook IDs are stable, but ASLR changes native addresses per process. An export name alone proves neither its signature nor object ownership. Private bindings require the documented fingerprints and prologue/ABI evidence; unsupported adapters report unavailable instead of guessing offsets.

Reservations coordinate participating hook owners, not every framework in the process. A catalog address is the native entry, possibly already patched, not an unhooked trampoline. Existing RE_Kenshi, Dust or KenshiLib DLLs are not automatically compatible with the SDK.

09 / Experimental scenery path

One mesh.
Many placements.

The current experimental Forests replacement shares source geometry and adds a 48-byte affine transform for each supported placement.

Ordinary batching expands source vertices into placement-specific geometry. The replacement reads a live region’s build queue, clones native metadata that shares the original vertex/index buffers, and uploads transform rows instead. It preserves the region grouping, parent transform, bounds and visibility decisions. It does not need a baked placement file or save-specific asset bundle.

Eligibility is deliberately narrow

At least two placements must use one exact source SubMesh, white colors, positive uniform scale, unit quaternions, UV0 without extra texture-coordinate streams, and known object/shadow HLSL programs. Mixed sources, wind, animation and unsupported layouts retain the original builder.

Lifetime follows the region

Private material clones retain textures, fragment programs and constants. Clear restores original materials and declarations, removes clones and releases instance buffers. Disabling stops new replacements; existing optimized batches stay valid until their regions unload. Reload the save to rebuild loaded regions after changing the setting.

10 / Preferences & retirement

Live settings.
Deliberate shutdown.

Plugins declare controls once. The host generates the menu, validates changes and coordinates persistence with the owning plugin.

Static Setting declarations become toggles or bounded numeric controls in Options → REKENSHI-RUST. IDs and setting keys must be unique; keys should be namespaced. The same native tab presents built-in and external controls, including unavailable reasons. Native tabs own their widgets, and closing/reopening Options reconstructs the tab rather than reusing dead widgets.

Rollback

Persistent configuration

RE_Kenshi_Rust/
├─ modpack.toml          # built-in settings
├─ plugins.toml          # discovery + load order
├─ shader-cache.toml     # startup cache budget
├─ plugins/*.dll         # independent mods
└─ settings/<id>.toml    # per-DLL settings

Some legacy effect/cache configuration remains startup-only. Replacing DLL code requires restart; individual features such as scenery rebuilding also have specific activation limits.

Reverse the dependency direction

Host stop disables gameplay dispatch and callback readiness, stops external DLLs in reverse load order, then stops built-ins in reverse registration order. Managed callback groups are detached and admitted calls are awaited before their plugin cleanup. Providers revoke ownership before retiring resources.

Plugins must join their workers and release resources even after partial startup. Failed native shutdown can retain ownership and pinned state. Trampolines and module code stay mapped for process life; “stopped” does not mean “unloaded from memory.”

Install and restore are separate from plugin lifetime. The installer backs up engine configuration and preserves user settings and DLL files. Restore checks the installed configuration hash before replacement, so independent edits are not silently overwritten. This host does not promise full feature parity with the original RE_Kenshi.

Build an ordinary mod

cargo install --path tools/cargo-rekenshi --locked
cargo rekenshi new plugin my-mod
cargo rekenshi new plugin my-look --kind graphics

Implement Plugin, declare settings, keep owned registrations in state and use export_plugin!. No host registry edit or custom MyGUI wiring is required for an independent DLL.

Add a native capability

Establish the binary identity, exact ABI, legal thread, forwarding behavior and allocation/retirement contract. Put verified native access in a provider and expose copied operations or a typed SDK client. A discovered symbol is a research lead, not a finished binding.

Use register for desired rules, install for native activation, settings_changed for validated preferences, and stop for cleanup. Existing start/update methods remain default aliases.

Workspace crates use Rust 2024 and a declared minimum Rust version of 1.85. The root is a Windows x64 cdylib; the default release build also builds the separate Kenshi 2 style sample. A workspace build includes the other samples and compatibility fixtures. Windows MSVC linking and the Windows SDK are required.

12 / Verification & scope

Prove each boundary.
Keep the limits visible.

Compilation, native ownership tests, pixel checks and a loaded-world experiment answer different questions. None substitutes for all the others.

The repository’s complete workflow is scripts/verify.ps1 -KenshiDir <install>. It checks formatting, warnings-denied Clippy, workspace and documentation tests, public docs and release builds, then exercises installation, native forwarding, independent DLL lifecycle/settings, caches, gameplay transport, UI, weather, graphics state/pixels and instancing fixtures. Passing fixture evidence does not certify every hardware combination, game build or mod stack.

Safe behavior

Runtime tests cover dependencies, duplicates, settings rollback, operation ordering, pending rules, generations, overflow, recursion, panic quarantine and in-flight shutdown.

Native contracts

Fixtures load actual supported libraries and test allocation/adoption/release, original-operation fallback, repeated lifecycle transitions and independent DLL boundaries.

World evidence

Loaded-game checks establish visual behavior and representative performance. Logical resource bytes, process commit, resident working set and dedicated VRAM are different measurements.

Implemented today, with verified-adapter limits

Public desired registrations and composition; mandatory preparation; provider generations and copied events; shared post-tonemap effects; weather and dark UI policies; cache/codec providers; copied player-roster snapshots and supported queued commands; diagnostics/resource capture; experimental single-source scenery replacement.

Proposed or still missing native evidence

Full world loading/unloading phases, save/load/import identity and completion, verified physics SDK pre-destruction notification, device loss before teardown, whole UI/particle hierarchy readiness, arbitrary native reskinning and additional postprocess stages remain unsupported. The broader platform specification’s spawning, AI, time and persistence interfaces are proposals, not available SDK promises.

Documented Rust guideline exceptions remain visible

The implementation record retains a pointer-free C-descriptor/transport-status model in the safe registry instead of a fully separate native core/error model (M-FFI-TRANSLATES, M-ERRORS-CANONICAL-STRUCTS). Process-pinned detours, codec state and DLL-local guards retain the M-AVOID-STATICS exception. Panic containment requires restart (M-PANIC-CONTINUATION). Native ABI/lifetime reasoning and local allocation ownership follow M-UNSAFE, M-UNSOUND and M-ISOLATE-DLL-STATE. The physics pre-destruction limitation is unresolved. This guide is an architectural explanation, not a complete guideline audit; Miri cannot validate Windows detours or COM behavior.
